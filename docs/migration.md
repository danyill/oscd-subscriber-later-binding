# Migration to the standalone plugin stack

Worklog for Phase 4 of `docs/test_plan.md`: replace the legacy UI and libraries
with the standalone OpenSCD stack, and break the 3,400 line component apart. The
specs from Phases 0 to 3 are the safety net, and only `src/testing/` should need
to change for a given library or UI change.

## Metadata

* Branch: `plugin-migration`, based on `test-suite-overhaul`.
* Reference plugin for structure, style and virtualized lists:
  [`oscd-editor-subscriber-databinding`](https://github.com/OMICRONEnergyOSS/oscd-editor-subscriber-databinding).
  It handles early binding. This plugin handles later binding (ExtRefs with
  `intAddr`), so the approach is reused, not the functionality.
* Recipes followed (from the migration skill): `scl-lib`, `oscd-api`,
  `editv1-to-editv2`, `mwc-to-oscd-ui`, `oscd-ui`, `scl-icons`,
  `filtered-list-to-oscd-ui`, `scoped-elements`, `lit-translate-to-lit-localize`,
  `code-structure`, `implementation-hardening`.

## Design

### Why this shape

The monolith mixes five things: persisted settings, derived indexes and caches,
which rows to show, rendering, and edit dispatch. Everything is reachable from
every method, so nothing could be tested without rendering. The databinding
plugin separates a root plugin from list components, uses a shared virtualized
filtered list, and keeps SCL logic in plain modules.

### Layout

```
src/
  oscd-subscriber-later-binding.ts   root: state, settings, layout, edit flow
  components/
    virtualized-filtered-list.ts     search field plus @lit-labs/virtualizer
    fcda-list.ts                     control blocks and FCDAs
    publisher-extref-list.ts         subscribed and available ExtRefs of an FCDA
    subscriber-extref-list.ts        IEDs and their ExtRefs
    list-menus.ts                    filter, sort and settings buttons
    subscription.ts                  events and shared styles
  foundation/
    settings.ts                      persisted settings: defaults, parse, serialise
    model.ts                         indexes for one document and control type
    restrictions.ts                  pXX checks against the model
    rows.ts                          which rows each list shows, in what order
    markdown.ts                      Markdown export
    actions.ts                       subscribe and unsubscribe edits
    (existing) search, sort, identity, extref, scl helpers, subscription
  testing/                           mount helper, page-object driver, queries
```

### State and data flow

* The root component owns all state: settings, view, control type and the
  selected FCDA, control block and ExtRef. It keeps the existing property names,
  so the specs and the attributes read by external menu plugins are unchanged.
* Child components are presentational. They take the model and state as
  properties and emit events (`fcda-select`, `extref-select`,
  `settings-change`). Edits are dispatched with `newEditEventV2` and bubble to
  the host.
* `SubscriptionModel` (`foundation/model.ts`) is built in `willUpdate` whenever
  `doc`, `docVersion` or the control type changes, as in the databinding plugin.
  It replaces the per-edit cache invalidation and its `window` listeners: after
  an edit the host raises `docVersion` and the indexes are rebuilt in one pass
  over the ExtRefs.
* Rows are plain data built by pure functions in `rows.ts` (control, FCDA, IED
  and ExtRef rows with search text), so filters, sorting and disabling are unit
  tested without a DOM. Components only render rows.

### Virtualization

Lists render through `@lit-labs/virtualizer`, so only the rows in view are in the
DOM. Filters and sorting act on the row data and so no longer hide items with CSS.
Specs mount the plugin in a container tall enough to render every row, so the
page-object driver can still read whole lists. Screenshot tests use a fitted
container.

### Trade-offs

* Rebuilding the model on every `docVersion` is simpler and testable but costs a
  pass over all ExtRefs per edit. The old code updated entries incrementally. The
  pass is linear and runs once per edit, as in the reference plugin.
* The root keeps about thirty properties for settings. This keeps the external
  contract and the specs stable, at the cost of a long property list. They are
  declared from one settings schema in `foundation/settings.ts`.

## Decisions

* DP-1: scope. Wizard editing is not restored (the monolith has a `TODO` for it),
  so `oscd-scl-dialogs` is not added.
* DP-2: `nsdoc` is not used by this plugin and is not added.
* DP-3: text is wrapped in `msg()` from `@lit/localize`, English only.
* DP-4: the settings persistence defects found by the specs are fixed in the new
  settings module, and the skipped specs are enabled.
